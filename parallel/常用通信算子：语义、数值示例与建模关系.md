# 常用通信算子：语义、数值示例与建模关系

整理日期：2026-10-05。

## 1. 常用的有多少类

面向大模型训练、推理和性能建模，可以先掌握 **10 类操作：8 类搬运或归约数据的集合通信，加上 Send/Recv 点对点通信和 Barrier 同步**。这是本文的学习分类，不是所有通信库的 API 总数。Send 和 Recv 是两个配套操作，本文合为一类；Barrier 本身也属于集合操作，这里按同步用途单列。

| 类别 | 操作 | 核心作用 |
| --- | --- | --- |
| 集合通信 | Broadcast | 一个来源，把同一份数据分发给组内所有参与者 |
| 集合通信 | Scatter | 一个来源，把不同数据块分发给不同参与者 |
| 集合通信 | Gather | 各自提供数据，集中到一个接收者 |
| 集合通信 | AllGather | 各自提供数据，每个参与者都收到完整集合 |
| 集合通信 | Reduce | 对应位置做归约，完整结果交给一个接收者 |
| 集合通信 | AllReduce | 对应位置做归约，每个参与者都有完整结果 |
| 集合通信 | ReduceScatter | 对应位置做归约，每个参与者获得结果的一块 |
| 集合通信 | AllToAll | 每个参与者按目标发送不同的数据块 |
| 点对点通信 | Send / Recv | 指定发送方与接收方传递数据 |
| 同步 | Barrier | 等待组内所有参与者到达同步点 |

集合通信的基本语义可对照 [NCCL Collective Operations](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)；点对点与同步分别见 [NCCL P2P](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/p2p.html) 和 [PyTorch Barrier](https://docs.pytorch.org/docs/2.14/distributed.html#torch.distributed.barrier)。具体后端与版本支持哪些接口，需要另外核对。

## 2. 读例子前的约定

- **Rank**：通信组内参与者的编号。下面使用 R0、R1、R2、R3，示例假设一个参与者对应一张 GPU；Rank 编号与物理 GPU 编号不是同一个概念。
- **通信组（Communicator / Process Group）**：本次操作的参与者集合。“所有”指组内所有 Rank，不一定是整个集群。
- **Root**：指定的数据来源或结果接收者。需要 Root 的例子统一取 R0。
- **归约（Reduction）**：对不同 Rank 的对应元素执行求和、最大值等运算。下面统一使用 SUM。
- 所有例子都是自行构造的整数语义示例，不是性能实测。数组中的数字表示数据值，不是数据大小。

## 3. 每种操作如何工作

### 3.1 Broadcast：大家拿到同一份数据

R0 持有 `[7, 8]`，希望组内其他 Rank 得到相同数据：

```text
输入：R0 = [7, 8]

Broadcast(root=R0) 后：
R0 = [7, 8]
R1 = [7, 8]
R2 = [7, 8]
R3 = [7, 8]
```

用途示例：一个 Rank 读取配置或权重后，将其广播给需要相同副本的其他 Rank。其他 Rank 原有缓冲区内容不参与计算。

### 3.2 Scatter：一份大数据分给大家

R0 持有完整数组，将它切成四个块，各 Rank 接收自己的块：

```text
输入：R0 = [1, 2 | 3, 4 | 5, 6 | 7, 8]

Scatter(root=R0) 后：
R0 = [1, 2]
R1 = [3, 4]
R2 = [5, 6]
R3 = [7, 8]
```

用途示例：数据只在 R0 上时，把一个批次切成不同子批次分发。Broadcast 给大家同一份内容；Scatter 给大家不同块。这里的 Scatter 是跨 Rank 通信，与单卡张量索引操作 `torch.scatter` 不同。参考 [Open MPI Scatter](https://docs.open-mpi.org/en/main/man-openmpi/man3/MPI_Scatter.3.html)。

### 3.3 Gather：大家的数据集中到一处

各 Rank 提供一个块，R0 按 Rank 顺序收集：

```text
输入：
R0 = [1, 2]
R1 = [3, 4]
R2 = [5, 6]
R3 = [7, 8]

Gather(root=R0) 后：
R0 的接收结果 = [1, 2, 3, 4, 5, 6, 7, 8]
其他 Rank 不获得完整的 Gather 输出。
```

用途示例：各 Rank 分别计算结果，集中到一个 Rank 保存。Gather 保留各方数据，按顺序放入结果，没有求和。参考 [Open MPI Gather](https://docs.open-mpi.org/en/main/man-openmpi/man3/MPI_Gather.3.html)。

### 3.4 AllGather：大家的数据，每个人都收齐

输入与 Gather 相同，区别在于结果分布：

```text
输入：R0=[1,2]，R1=[3,4]，R2=[5,6]，R3=[7,8]

AllGather 后：
R0 = [1, 2, 3, 4, 5, 6, 7, 8]
R1 = [1, 2, 3, 4, 5, 6, 7, 8]
R2 = [1, 2, 3, 4, 5, 6, 7, 8]
R3 = [1, 2, 3, 4, 5, 6, 7, 8]
```

用途示例：每卡持有权重的一块，某次计算需要完整权重时，将这些块收齐。这里展示的是一维缓冲区；若原张量沿其他维度分片，恢复逻辑布局还可能需要本地重排。参考 [NCCL AllGather](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html#allgather)。

### 3.5 Reduce：算出合并结果，交给一个 Rank

四个 Rank 的输入具有相同长度，对应位置相加：

```text
输入：
R0 = [   1,    2,    3,    4]
R1 = [  10,   20,   30,   40]
R2 = [ 100,  200,  300,  400]
R3 = [1000, 2000, 3000, 4000]

Reduce(SUM, root=R0) 后：
R0 的接收结果 = [1111, 2222, 3333, 4444]
其他 Rank 不获得有效的完整归约结果保证。
```

用途示例：各 Rank 计算本地 token 数量，将数量求和到 R0，用于集中记录。**跨 Rank 的 Reduce 不会自动把数组内部所有元素再合成一个标量**；上面四元素输入对应四元素输出。参考 [NCCL Reduce](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html#reduce)。

### 3.6 AllReduce：算出合并结果，每个人一份

使用与 Reduce 相同的四组输入：

```text
AllReduce(SUM) 后：
R0 = [1111, 2222, 3333, 4444]
R1 = [1111, 2222, 3333, 4444]
R2 = [1111, 2222, 3333, 4444]
R3 = [1111, 2222, 3333, 4444]
```

用途示例：TP 矩阵乘法产生对同一输出的不同局部贡献，下游需要每卡持有完整输出时，对局部贡献做 AllReduce(SUM)。SUM 不自动除以 Rank 数量；需要均值时必须明确均值语义或另行缩放。参考 [NCCL AllReduce](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html#allreduce)。

### 3.7 ReduceScatter：算出合并结果，每个人只拿一块

仍使用 Reduce 的四组输入。可以在数学上先想象归约结果 `[1111, 2222, 3333, 4444]`，再按 Rank 分块：

```text
ReduceScatter(SUM) 后：
R0 = [1111]
R1 = [2222]
R2 = [3333]
R3 = [4444]
```

用途示例：每卡先产生完整形状的局部梯度贡献，归约后每卡只负责其中一段梯度的后续处理。ReduceScatter 也可用于计算结果从待归约布局转为分片布局。

“先归约再切分”用于理解语义，实际算法不必先在某一张卡上存放完整归约结果。它输出的是**归约后的切片**，而 Scatter 分发的是 **Root 原有数据的切片**。参考 [NCCL ReduceScatter](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html#reducescatter)。

### 3.8 AllToAll：每个人给不同目标发送不同块

每个 Rank 有四个块，块的位置决定目标 Rank。为简化示例，每块只有一个元素：

```text
输入：             发给R0  发给R1  发给R2  发给R3
R0                   0       1       2       3
R1                  10      11      12      13
R2                  20      21      22      23
R3                  30      31      32      33

AllToAll 后：      来自R0  来自R1  来自R2  来自R3
R0                   0      10      20      30
R1                   1      11      21      31
R2                   2      12      22      32
R3                   3      13      23      33
```

把输入看作“来源 × 目标”的矩阵，输出展示了各目标收到的一列。AllToAll 不执行求和，每张卡也没有收到所有 16 个元素。相同 Rank 的自发自收可以在本地处理，不应默认计入跨设备网络流量。基本语义见 [NCCL AllToAll](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html#alltoall)。

用途示例：MoE 的 EP（Expert Parallel，专家并行）把 token 发往目标专家所在 Rank，计算后再把结果送回。完整 Dispatch/Combine 还可能包含复制、分桶、重排、加权求和，不能只用一次 AllToAll 代表全部工作。可继续阅读已有的 [EP 分析](ep-inference-analysis.md)。

### 3.9 Send / Recv：指定两端之间传递数据

```text
R1 持有 [9, 8, 7]

R1：Send([9, 8, 7], dst=R2)
R2：Recv(src=R1)

结果：R2 的接收缓冲区得到 [9, 8, 7]
R0、R3 不需要参与这次传输。
```

Send 描述发送端，Recv 描述接收端，两者共同完成一次匹配传输。发送不是转移数据所有权，原数据不会因为 Send 自动删除。

用途示例：PP（Pipeline Parallel，流水线并行）的前一个 stage 将激活传给后一个 stage。多组 Send/Recv 还可以组织成环形交换等通信模式。参考 [NCCL Point-to-point communication](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/p2p.html)。

### 3.10 Barrier：大家到齐，才能继续

```text
各 Rank 到达同一个 Barrier 的时刻：
R0：3 ms
R1：5 ms
R2：4 ms
R3：8 ms

忽略 Barrier 协议本身的开销：
最早放行时刻为 8 ms。
R0、R1、R2、R3 的等待时间分别为 5、3、4、0 ms。
```

Barrier 不生成新的业务张量值，但底层可能需要交换同步信号或执行小型通信。实际放行还要考虑协议开销，各 Rank 也不必在完全同一时刻返回。参考 [PyTorch Barrier](https://docs.pytorch.org/docs/2.14/distributed.html#torch.distributed.barrier)。

用途示例：在明确要求所有参与者就绪后，再开始下一阶段。其他集合通信要求匹配参与，不意味着每次集合通信都自动具有独立 Barrier 的全部同步语义；也不应默认在每个通信前后添加 Barrier。

## 4. 一个重要变体：AllToAllV

前面的 AllToAll 使用等长数据块。**AllToAllV 允许对不同目标发送不同数量的数据**，发送方和接收方必须约定一致的数量与位置。参考 [Open MPI Alltoallv](https://docs.open-mpi.org/en/main/man-openmpi/man3/MPI_Alltoallv.3.html)。

例如三个 Rank 交换 token 编号，空列表表示该方向没有数据：

```text
                   发给R0      发给R1       发给R2
R0                 [0]         [1, 2]       []
R1                 [10, 11]    []           [12]
R2                 []          [20]         [21, 22]

交换后，按来源 Rank 排列：
R0 = [0, 10, 11]
R1 = [1, 2, 20]
R2 = [12, 21, 22]
```

对应的发送元素数量矩阵为：

```text
        目标0  目标1  目标2
来源0      1      2      0
来源1      2      0      1
来源2      0      1      2
```

这个例子各 Rank 总接收量恰好相等，但每对 Rank 间的流量不同；一般情况下总接收量也可以不等。MoE 路由中不同专家接收的 token 数可能不同，因此建模需要保留流量矩阵或明确的不均衡假设，不能只用总字节数除以 EP。

AllToAllV 是语义名称，不保证每个通信库都提供同名原生接口。PyTorch 的 [all_to_all_single](https://docs.pytorch.org/docs/2.14/distributed.html#torch.distributed.all_to_all_single) 使用 split sizes 表达不等长划分，实际可用性还取决于后端。

## 5. 三组最容易混淆的关系

### 拼接与归约

```text
R0=[1, 2]，R1=[10, 20]

AllGather → 每卡 [1, 2, 10, 20]：保留两份数据
AllReduce → 每卡 [11, 22]：对应位置求和
```

### 语义等价与实现成本

在通信组、数据布局和归约操作匹配时，数学结果上有：

```text
AllReduce ≡ Reduce → Broadcast
AllReduce ≡ ReduceScatter → AllGather
```

这是语义等价关系，不代表实际 AllReduce 必须执行两个独立 API，也不代表耗时和临时显存相同。浮点数归约顺序改变时，还可能产生舍入差异。等价关系见 [NCCL Collective Operations](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)。

### 语义、算法和传输机制

- `AllReduce` 描述数据经过通信后应变成什么。
- `Ring`、`Tree` 等描述完成通信的组织算法。
- NVLink、PCIe、网络链路等影响数据实际经过的路径和资源。

因此不能把某个通信算子永久等同于某一种算法，也不能只根据算子名称确定耗时。这里是性能建模的设计判断，不是本文已经完成的性能测量结论。

## 6. 与模型分片和执行计划的关系

**通信往往是在解决“当前数据分布”和“下一步所需数据分布”之间的差异。**

三个布局术语：`Shard` 表示各卡持有不同切片；`Replicate` 表示各卡持有同一个完整副本；`Partial(SUM)` 表示各卡持有需要相加才能得到逻辑结果的局部贡献。

| 当前数据状态 | 后续需要的数据状态 | 常见操作 |
| --- | --- | --- |
| Shard：各卡持有不同块 | Replicate：每卡完整副本 | AllGather |
| Partial(SUM)：各卡是局部求和贡献 | Replicate：每卡完整结果 | AllReduce(SUM) |
| Partial(SUM) | Shard：每卡持有最终结果的一块 | ReduceScatter(SUM) |
| 沿一个维度分片 | 沿另一个维度分片 | AllToAll，必要时加本地重排 |
| Replicate：各卡已有完整副本 | Shard | 本地切片即可 |
| 数据只在一个来源上 | 每卡完整副本 / 各卡不同块 | Broadcast / Scatter |
| 数据在上一个流水阶段 | 下一个阶段需要它 | 匹配的 Send / Recv |

前五项可与 [PyTorch DTensor 的 redistribute 文档](https://docs.pytorch.org/docs/2.14/distributed.tensor.html#torch.distributed.tensor.DTensor.redistribute) 对照。这里讨论相应通信组/设备网格维度内的布局转换，多维网格、不等长分片和物理布局可能需要组合操作。

例如，TP 矩阵乘法的每卡输出同为 `[2, 8]`，可能是 Partial，也可能是 Replicate。仅靠 shape 不能判断它是否还需要 AllReduce。相反，每张卡已经有完整副本时，为获得自己的切片而执行 Scatter，会凭空增加不必要的通信。

对拟设计的执行计划生成器，建议记录通信类型、参与 Rank、Root 或对端、输入输出引用、归约操作、数据类型、每对 Rank 的有效数据量、依赖与完成条件；再由实现选择与仿真层决定算法、路径、资源占用和完成时间。这是设计建议，不代表现有建模代码已实现。

## 7. 性能和显存建模边界

以下是从语义推导出的建模要求：

1. **区分逻辑数据量与网络流量。** AllGather 的本地输入、最终输出、经过网络的发送量是不同口径；环形转发还会经过多个 Rank。不能将接收缓冲区大小直接当作总链路流量。
2. **区分输出大小与峰值显存。** 等长 AllGather 中，每卡输入 n 个元素，输出为 P×n；ReduceScatter 中，每卡输入 n，输出为 n/P。峰值还依赖输入输出是否共存、是否原地执行、临时缓冲区和其他任务。
3. **区分等待与通信服务时间。** 某 Rank 到达较晚，其他 Rank 的等待不是链路本身变慢。模型应保留到达依赖，并按所选算法决定能否提前推进。
4. **允许同一语义有不同实现。** 不同算法、消息规模、拓扑和并发竞争可以导致不同耗时；解析估计需要明确假设，精确度提升需要相应测量。
5. **不将 API 异步返回等同于通信完成。** 下游计算使用接收数据、发送缓冲区复用或释放，都需要相应的完成依赖。
