# 探针：用小实验验证局部行为

## 问题：探针是什么

探针（probe）是一个为了回答单个具体问题而编写的小型验证程序。它不运行完整系统，而是取出最关键
的函数、公式或状态转换，给出可控输入，再检查输出、异常或状态变化。

例如，要确认一个推理框架怎样把 34 层模型分给 4 个 Pipeline Parallelism（PP）stage，可以直接
调用负责切层的函数，检查各 rank 是否得到 `[0,8)`、`[8,16)`、`[16,25)`、`[25,34)`。这个实验
回答的是“切层规则是什么”，不回答“完整推理服务能否运行”或“PP 性能是多少”。

探针不是某个固定测试框架，也不是生产代码中的监控探针。这里讨论的是调研和建模阶段使用的
一次性或可重复小实验。

## 为什么使用探针

复杂推理框架通常依赖 GPU、模型权重、通信库和大量 Python package。直接启动完整服务时，一次失败
可能来自环境、依赖、配置、硬件或功能本身，难以判断真正原因。

探针把问题缩小为：

> 在锁定的源码版本中，函数 F 收到输入 X 时，实际产生什么结果？

这样可以把“框架的确定性规则”与“当前机器能否启动完整服务”分开。它适合验证 shape、dtype、层
归属、rank 归属、执行次数、字节公式和状态转换等 T1 事实。T1 是建模期：源码本身可以提供真值，
目标是产出可复算断言。

没有直接依赖源码行为的问题不应优先用探针。例如 Kernel 时延、NCCL 实际带宽和 CUDA stream 重叠
依赖真实运行环境，应进入 T2 校准期，通过 Trace 和 Benchmark 观察。

## 探针怎样工作

一个合格的探针通常经过下面六步：

1. 把问题缩成一句可以判真假的话，例如“`n=1` 时 NEXTN draft 内循环执行零次”。
2. 锁定代码 revision，并找到真正决定该行为的函数或状态机。
3. 构造最小输入，避免把不相关模块一起带入实验。
4. 执行原实现，记录返回值、异常、调用次数或状态变化。
5. 使用精确断言验证结果，并补充 0、1、不能整除等边界输入。
6. 保存 revision、命令、输入、结果以及这个实验不能证明什么。

最简单的行为探针如下：

```python
for rank in range(4):
    begin, end = get_pp_indices(34, rank, 4)
    print(rank, begin, end)

assert [get_pp_indices(34, rank, 4) for rank in range(4)] == [
    (0, 8),
    (8, 16),
    (16, 25),
    (25, 34),
]
```

关键不是脚本短，而是问题边界明确、输入可控、结果可以被另一人独立复算。

## 源码隔离探针是什么

有时框架顶层 package 无法导入。例如导入一个切层函数时，初始化链路可能先加载 GPU backend、
`orjson` 或通信库。此时可以使用源码隔离探针：从原始源码中提取被验证的函数，并为无关依赖提供
最小 stub。

AST（Abstract Syntax Tree）是 Python 源码解析后的结构树。使用 AST 可以准确定位函数定义，避免
复制错代码或用字符串截取到错误范围。stub 是只实现被测函数所需接口的简化对象，例如只包含
`pp_size` 和 `rank` 的配置对象。

源码隔离探针的典型流程是：

```text
锁定 commit
    ↓
AST 读取原始函数
    ↓
补充最小常量和 stub
    ↓
执行原函数
    ↓
检查精确结果和不变量
```

stub 只能替代日志、配置容器等外围依赖。如果通信行为、Tensor 运算或 scheduler 时序本身就是验证
对象，就不能用 stub 把它们替掉，否则实验已经改变了被测语义。

## 一个推理建模中的实例

验证 Decode Context Parallelism（DCP）的 KV owner 规则时，可以遍历多组 DCP size、KV length 和
start offset，并检查下面三个不变量：

```text
所有 rank 的 token 数之和 = 全局 token 数
每个 token 恰好属于一个 rank
owner(position) = position mod DCP size
```

这比只测试一个正常样例更可靠。例如 `length=10,DCP=4` 应得到 `[3,3,2,2]`，但还要覆盖
`length=0`、`DCP=1`、长度不能整除和非零 start offset，才能发现边界偏差。

另一个例子是 NEXTN。探针可以记录一轮中模型 forward 的调用位置和输入行数，从而验证：draft 内
循环执行 `n-1` 次、target verify 输入 `n+1` 行、轮末 draft-extend 也输入 `n+1` 行。这能证明状态机
的结构工作量，但不能直接推出各段时延，因为不同 shape 的 Kernel 效率和重叠方式并不相同。

## 怎样区分探针失败和功能失败

实验记录不能只写“failed”。至少需要区分四种状态：

| 状态 | 含义 | 可以得出的判断 |
|---|---|---|
| `environment_failed` | 缺依赖、GPU 不可用或 package root 配错 | 环境不满足，不能判断功能 |
| `probe_failed` | 探针提取错函数、stub 不完整或脚本自身报错 | 探针需要修正，不能判断功能 |
| `assertion_failed` | 原实现输出与事先定义的断言不一致 | 存在可调查的行为冲突 |
| `passed` | 指定输入下的全部断言成立 | 只证明已覆盖范围内的局部行为 |

package root 是 Python 查找顶层 package 的起点。如果代码写
`from backend.inference...`，搜索路径应包含仓库根目录，而不是 `backend/` 本身。package root 配错
导致的 import failure 属于环境或探针问题，不能解释为被测功能错误。

## 探针与其他证据的关系

| 证据方法 | 主要回答的问题 | 主要局限 |
|---|---|---|
| 静态源码阅读 | 代码看起来要做什么 | 容易漏分支、调用次数和运行时选择 |
| 探针 | 局部规则在指定输入下实际做什么 | 不覆盖完整系统和真实硬件 |
| Unit Test | 一个模块是否持续满足项目内部合同 | 内部测试可能锁定了错误合同 |
| Integration Test | 多个模块组合后接口和状态是否正确 | 通常仍会模拟部分外部组件 |
| E2E Test | 请求经过完整服务后结果是否正确 | 成本高，失败时定位较慢 |
| Trace | 真实运行中执行了哪些 Kernel、通信和时间线 | 需要可运行环境，数据解释成本高 |
| Benchmark | TTFT、TPOT 和吞吐最终是多少 | 结果不能单独说明偏差来自哪一层 |

这些方法不是互相替代。合理的证据链通常是：先用源码和探针确定结构合同，再用 Unit Test 固化它，
用 Integration/E2E 验证组合流程，最后用 Trace 和 Benchmark 校准运行时效率。

## 如何评审一个探针

评审时应检查以下问题：

- 是否记录了仓库、commit 和被测函数位置；
- 是否执行原始实现，而不是重新手抄一份同名公式；
- stub 是否只替代无关依赖；
- 输入是否包含正常值和关键边界；
- 断言是否检查具体 shape、dtype、owner、字节数或状态；
- 输出是否能由另一位开发者独立复算；
- 记录是否明确说明探针不能证明的内容。

`assert result is not None` 不是有价值的行为断言。更好的断言是
`assert owner_counts == [3, 3, 2, 2]`，因为它明确说明了观测点和预期值。

## 为什么不总是启动完整服务

完整服务最接近真实行为，但不是所有问题都值得从 E2E 开始。为了确认一个纯切分函数而安装整套 GPU
依赖，成本高，失败噪声也大。只阅读源码则容易漏掉跨函数状态和边界分支。因此，对确定性局部规则，
源码隔离探针通常是成本与证据强度之间更合适的选择。

这个选择在以下条件下会失效：行为依赖 CUDA Kernel 内部逻辑、异步通信、多线程 scheduler、动态
dispatch，或者 stub 替代了决定结果的组件。遇到这些情况，必须升级到 Integration Test、E2E、
GPU Trace 或真机 Benchmark。

## 我不确定的地方

“探针”在不同团队中可能也指生产环境的 observability probe，例如健康检查、eBPF probe 或监控采样。
本文只讨论建模和调研时的局部行为实验。团队文档引用这个词时，最好同时写明
`source-isolation probe`、`runtime probe` 或 `production probe`，避免语义混淆。
